# Notes on the records

Background for readers who inspect the configuration and audit files in detail. None of these points changes a reported number; `python aura_cxr.py verify` checks the values that matter.

## Naming and structure

- **"Patient" in identifiers.** Column names, configuration keys and comments such as `patientId`, `patient_id`, "patient-level" and "patient-disjoint" follow the RSNA field name `patientId` of the Kaggle release, which identifies an image rather than a person (Kaggle data description: "Each patientId corresponds to a unique image"). Splits and folds are disjoint at this `patientId` (image) level; the overlap at the level of NIH patients is quantified in `results/analysis/nih_patient_overlap/` (README, *NIH patient overlap*).
- **`q1` and `stage` labels.** File names, schema names and options containing `q1` (for example `q1_stats_report.py`, `aura_cxr_dl_pair_selection_q1_v17`) or `stage` numbers are internal version labels of the final pipeline and its analysis steps; they are kept because the run records and hashes refer to them.
- **Method names.** The quantitative attribution reported in the paper is LayerCAM with the layers, weights and token handling in `configs/xai_frozen.json`. Some option names, comments and the free-text column `xai_failure_reason` in `results/predictions/` keep the generic label "GradCAM" from the code's history; they refer to the same maps.
- **EVA-X-S structure.** The training-time specifications (`configs/frozen_config.yaml`, `configs/specs/deep_training_specification.json`, `configs/specs/deep_17_eva_model_structure.csv`) were written before the XAI analysis and mark the block count, embedding dimension and class token as not captured. They were verified afterwards on the frozen checkpoint: 384-dimensional embeddings, one leading class token and 196 patch tokens in row-major order (`results/analysis/transformer_xai/token_structure.json`, `configs/xai_frozen.json`). The official `eva_x_small_patch16` definition has 12 blocks, so the hooked `blocks.11` is the final block; the released checkpoint contains blocks 0 to 11. The local file name `eva_x_s_16.pt` in some records is the downloaded official `eva_x_small_patch16_merged520k_mim.pt`.

## Inference and descriptive measures

- **Deep-branch probabilities are MC-dropout means.** Every DenseNet121-XRV and EVA-X-S probability in the development OOF predictions, the locked RSNA test and the Kermany evaluation is the mean of 30 Monte Carlo dropout passes (dropout layers active, all other layers in inference mode; `mc_predict` in `scripts/train_xrv_backbone.py` and `predict` in `scripts/train_eva_x_backbone.py`; recorded in `configs/specs/deep_training_specification.json`). These means are the A8 meta-features. Only the spread of the 30 passes (`*_std`, `*_predictive_interval_width_95` in `results/predictions/test_predictions_full.csv`) is a post-hoc diagnostic. The EfficientNetV2S and ResNet50 OOF predictions are MC-dropout means in the same way. GPU inference was not run in bit-exact deterministic mode, so re-running inference with the released checkpoints can differ slightly from the released probabilities, which are the reference for every reported number.
- **A8 predictive width (Fig. 5, Section 5.1).** The A8 width is not a spread of A8 passes: the MC-dropout standard deviations of the two deep branches are propagated through the logistic stack with a delta-method approximation that treats the branches as independent, `std_A8 = p(1 − p) · sqrt((β_XRV·std_XRV)² + (β_EVA·std_EVA)²)` (the radiomics branch has no MC spread), and the width is `2 × 1.96 × std_A8` (`ensemble_predictive_uncertainty` in `scripts/aura_dl_pair_selection.py`; per-case values in `results/analysis/figure_data/F05_UNCERTAINTY_data.csv`). Because it scales with p(1 − p), its larger median for errors (0.1236 versus 0.0446) mainly reflects that errors lie closer to the decision threshold; the branch-level standard deviations (`xrv_std`, `eva_x_std` in `results/predictions/test_predictions_full.csv`) are similar for errors and correct predictions (medians 0.015 versus 0.018 for DenseNet121-XRV and 0.022 versus 0.021 for EVA-X-S). The width is a descriptive diagnostic, not a calibrated coverage interval.
- **XAI settings.** The attribution method (GradCAM, LayerCAM or HiResCAM), hooked layers, layer and model weights, map policy (raw or lung-softened) and localization threshold (0.25 to 0.75) were selected from a predefined grid on 255 GT-positive cases of the RSNA validation partition with the frozen deployment checkpoints (`results/audit/run_records/xai_cam_configuration_validation.json`, `xai_cam_layer_selection_validation.json`, `xai_cam_candidate_compatibility_validation.csv`); the validation images are part of the development cohort on which those checkpoints were refitted, and no locked-test box was used. The Gaussian smoothing width (σ = 0.005 × 224 = 1.12 pixels) was fixed in the code, not selected.
- **Outside-lung attribution.** The outside-lung values in the paper (mean 0.2155; TP 0.1823; FN 0.4056) are computed with the regenerated lung masks in `results/predictions/outside_lung_per_sample.csv` (`outside_lung_ratio_regenerated`, with the mask hash per case). The columns `outside_lung_ratio_raw` and `outside_lung_ratio_selected` in `results/predictions/xai_localization_per_sample.csv` and `results/metrics/xai_localization_summary.csv` (mean 0.0639) come from the larger lung masks of the original XAI run (`outside_lung_ratio_old` and `lung_mask_area_old` in the same file). The measure therefore depends on the lung mask, is reported only descriptively, and has no p-value family (`results/audit/analysis_qc.json`); the localization metrics against the RSNA boxes are computed on the raw, ungated maps (`map_policy: raw` in `configs/xai_frozen.json`) and do not depend on either mask.

## Hashes

- **Upstream checkpoint hashes.** The upstream files were loaded from library caches (TorchXRayVision, Keras) or a local copy (EVA-X-S), and their SHA-256 values were not recorded during training (`UNRESOLVED_FROM_AVAILABLE_PROVENANCE`). The SHA-256 values of the trained checkpoints were recorded, are listed in `configs/checkpoints.json`, and match the files of release v1.0. For reference, the public TorchXRayVision `densenet121-res224-all` file (https://github.com/mlmed/torchxrayvision/releases/download/v1/nih-pc-chex-mimic_ch-google-openi-kaggle-densenet121-d121-tw-lr001-rot45-tr15-sc15-seed0-best.pt) has SHA-256 `56524913dd16a906422e8d8b66a7a5c46be1d82eb7ac012d8103776f1aa68899` (checked 2026-10-21).
- **Configuration file hashes.** `frozen_config_file_sha256` in `configs/specs/deployment_manifest.json` and `results/audit/golden_reference.json`, and the hashes in some `input_hashes.json` files, identify the configuration file as it existed when those records were written. The released `configs/frozen_config.yaml` is a later, documentation-expanded version; the values that define A8 (meta-feature order, coefficients and threshold) are identical in this file, the deployment manifest, the golden reference and `src/aura_cxr/fusion.py`, and `verify` checks this together with the trained-checkpoint hashes.
- **Path placeholders.** Machine-specific directories in the records are replaced by `${WORK_DIR}`, `${AURA_PACKAGE_DIR}` or `${AURA_PROJECT_DIR}`. The EVA-X-S checkpoint is the exception: its `checkpoint` field still records the original server path of the upstream file, because the checkpoints are released unmodified so that they match the recorded hashes.

## Loading the trained checkpoints

- The PyTorch files hold a dictionary with `state_dict`, `dropout`, `refit_epochs`, `optimizer_updates`, `image_size` and `parameter_count`, and load with `torch.load(path, map_location="cpu", weights_only=True)`.
- They are loaded into the architectures built by `build_model` in `scripts/train_xrv_backbone.py` (with `weights=None`) and `scripts/train_eva_x_backbone.py` (which needs the official EVA-X code and upstream checkpoint).
- `xrv_infer` and `load_xrv_binary_state_dict_strict` in `scripts/external_validation_kermany.py` show the exact loading used for the external evaluation, including the one unused TorchXRayVision buffer (`backbone.op_threshs`) that is dropped before strict loading.
- The radiomics file loads with `joblib.load` under the pinned scikit-learn, LightGBM and joblib versions and takes the 746-feature vector of `src/aura_cxr/radiomics.py`. As a pickle, it should be loaded only after its hash has been checked.

- The comparator's initial mixed-precision run, which was replaced by the FP32 rerun, is documented in `results/analysis/contemporary_baseline/attempt1_amp_audit/`, with its raw outputs and per-case locked-test and OOF predictions in `initial_run_raw/`. `verify` checks that the record is internally consistent and reproduces its locked-test ROC-AUC from the per-case predictions.
- The raw server outputs of the reported FP32 run (log, fold-level results, refit record and bootstrap replicates) are in `results/analysis/contemporary_baseline/fp32_run_raw/`.
- The comparison of each selected encoder with ConvNeXt V2 Tiny is in `results/analysis/contemporary_baseline/15_COMPONENT_VS_BASELINE.csv`; the upstream pretraining data of every backbone are listed in `configs/specs/upstream_pretraining_data.csv`.
